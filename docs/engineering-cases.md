# 四个工程案例：问题、取舍与验证

案例来自实际项目代码。本页解释技术问题与实现，不代表候选人独立完成原系统的全部模块。

## 1. 同轮批量读取客户等级

**问题：** 客户列表和卡片分别挂载时，如果每个组件单独发请求，同一批界面可能产生重复读取。

**实现：** loader 将客户 ID 放入 Map，同一 ID 保留多个等待者；通过 `queueMicrotask` 合并同轮请求。刷新时先交换 pending Map，保证之后的请求进入新批次。每 100 个唯一 ID 分片，对重复请求分发同一结果；遗漏的 ID 返回 null，失败分片拒绝对应等待者，其他分片继续完成。

**取舍：** 它不是缓存，也不是全局并发限流器；后续轮次会再次读取。实例按账号创建，避免把多个账号的请求混在同一批次。接口按权限省略的 ID 与不存在的 ID 在此都表现为 null；不从结果推断客户是否存在。

**验证：** [测试](../tests/customer-grade-loader.test.ts)覆盖重复 ID、205 个唯一 ID 的分片、部分分片失败、同步异常、后续恢复与实例独立。该测试不代替服务端鉴权测试，也不代表实测性能提升百分比。

## 2. 日历日期不等同于时间戳

**问题：** 跟进日期和经营周期中的“某一天”不应该因为字符串归一化或隐式时区转换而改变含义。JavaScript Date 还存在低年份及无效日期自动归一化等容易忽略的细节。

**实现：** 严格接受 YYYY-MM-DD，检查公历闰年与每月天数；通过品牌类型限制后续日期运算。加减天数使用序号运算，显式检查范围；需要 UTC Date 时先验证，再使用 `setUTCFullYear`。

**取舍：** 支持范围是 0001-01-01 至 9999-12-31，拒绝格式宽松输入。该模块不负责公司时区的“当天起止时间”，调用方需在业务边界转换。

**验证：** [测试](../tests/calendar-date.test.ts)覆盖低年份、世纪闰年、非法日期、跨年、上下限、非整数偏移和 schema 校验。

## 3. 给并发入站建立一致的锁键顺序

**问题：** 消息重投或关联身份并发更新时，单靠进程内的去重不能协调多个数据库事务。多个资源的获取顺序还需要统一。

**实现：** 为消息 ID、非空 phone 与 waId 建立带命名空间的键，去除标识首尾空白，并使用明确的字符比较排序。调用方在事务中按这个顺序获取锁。

**取舍：** 锁键函数不做电话号码业务规范化、不获取锁、不写数据库，也不单独保证幂等。所有需要竞争同一资源的写入路径必须遵守共同约定；数据唯一约束仍不可缺少。

**验证：** [测试](../tests/inbound-identity-locks.test.ts)覆盖多个资源的顺序、首尾空白和空标识。测试中的 phone 是 `demo-phone`，不是真实联系方式。数据库锁和事务竞争没有在公开样例中运行。

## 4. 把模型输出限定为可核验的观察

**问题：** 模型生成的 JSON 即使可以解析，也可能混入越权的系统字段、没有依据的因素、重复引用或过量输出。

**实现：** Zod strict object 约束字段与枚举；每条因素必须带至少一条 message/note 引用；限制文本、因素和引用数量；禁止同一条目内的重复引用。观察中保留缺失信息与矛盾，不把观察直接当作最终分数。

**取舍：** 本样例只展示模型观察阶段，未包含完整评分合成。通过 schema 只能证明结构符合契约；引用是否存在、当前账号是否有权读取、原文是否支持判断，都要由领域服务继续验证。

**验证：** [测试](../tests/semantic-observation.test.ts)覆盖正常观察、额外系统字段、非法方向、缺失与重复证据、嵌套未知字段和数量限制，还特意验证“虚构引用仍可能通过结构校验”，避免夸大 schema 的保障范围。
